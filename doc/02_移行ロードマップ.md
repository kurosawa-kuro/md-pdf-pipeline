# 移行ロードマップ

> **本リポジトリの決定的仕様**。何を作るか・何を作らないかの最終決定。
> スコープ確定・方針変更時に更新する。矛盾時はこのドキュメントを正とする。

## 0. 前提

- **成果物**: `WSL + Python + WeasyPrint` を前提とした、Markdown から日本語 PDF を生成するローカル CLI パイプライン
- **設計の正**: 機能仕様、アーキテクチャ、採用技術、非機能要件は [`01_仕様と設計.md`](./01_仕様と設計.md) を正とする。本書はその実行順と採否を固定する
- **初期スコープ**:
  - 単一 Markdown 入力
  - 単一 PDF 出力
  - `WSL2 + Ubuntu + Python 3`
  - `Python + WeasyPrint` を本命実装とする
  - ローカル CLI 実行のみ
- **スコープ境界**:
  - Markdown 読み込み
  - HTML 化
  - HTML テンプレート適用
  - CSS 適用
  - PDF 出力
  - ローカル保存
- **対象外**:
  - Google Drive 連携
  - クラウド同期
  - Web UI
  - GUI 依存運用
  - 複数ファイル一括変換
  - PDF 編集、注釈、OCR
- **前提ディレクトリ状況**: `src/` は現時点で空であり、本書で初期構成まで決める

## 2. 段階構築計画

> 初期版は単一 Markdown を単一 PDF へ変換する最短経路を対象とする。
> Google Drive や GUI は Phase 外とし、ローカル CLI の再現性を優先する。

### Phase 0: プロジェクト初期化

- 内容:
  - `src/` 配下の初期構成を定義する
  - 主要ファイル責務を以下で固定する
    - `src/cli.py`: 引数受付、終了コード、全体起動
    - `src/markdown_loader.py`: Markdown 読み込み、パス解決
    - `src/html_renderer.py`: Markdown → HTML 変換、HTML 骨格適用
    - `src/pdf_renderer.py`: WeasyPrint 呼び出し、PDF 出力
    - `src/templates/`: HTML テンプレート置き場
    - `src/styles/`: 印刷用 CSS 置き場
    - `src/examples/`: 検証用 Markdown
    - `out/`: 既定 PDF 出力先
  - 入出力方針を固定する
    - 入力 = 単一 UTF-8 Markdown
    - 出力 = 単一 PDF
    - 既定出力先 = `out/`
- 完了条件:
  - 初期ディレクトリ構成が決まっている
  - 入出力方針、依存方針、主要ファイル責務が記述済み
  - `01` のアーキテクチャ図と矛盾しない

### Phase 1: 最小 CLI 実装

- 内容:
  - 単一 Markdown を読み、単一 PDF を出力する最短経路を実装する
  - Markdown 読み込み
  - Markdown → HTML 変換
  - HTML → PDF 変換
  - 成功時 / 失敗時の終了コード設計
- 入力仕様:
  - 入力ファイルパスを 1 つ受け取る
  - 入力未存在時は即失敗する
- 出力仕様:
  - PDF を 1 ファイル生成する
  - 正常終了時は生成パスを標準出力へ出す
- 完了条件:
  - 単一 `.md` から `.pdf` を生成できる
  - 入力未存在時に明示的に失敗する
  - 依存未導入時に意味の分かるエラーを出す

### Phase 2: 印刷品質の安定化

- 内容:
  - HTML テンプレート層を実装する
  - 印刷用 CSS を実装する
  - 日本語フォント指定を組み込む
  - 次の要素の見た目を固定する
    - 本文
    - `h1`〜`h3`
    - テーブル
    - `code` / `pre`
    - `blockquote`
- 前提:
  - 日本語フォントは `Noto Sans CJK JP` 系を本命とする
  - 横長テーブルは完全解決を目指さず、Markdown 側の見直しも許容する
- 完了条件:
  - 日本語が文字化けしない
  - 表、コードブロック、見出しが最低限読める
  - A4 余白ありで出力される

### Phase 3: 運用性と設定の追加

- 内容:
  - 出力先指定を追加する
  - 上書き制御方針を決める
  - 実行ログ方針を決める
  - 非機密設定の切り出し先として `env/config.yaml` の扱いを定義する
  - `Makefile` への反映先を定義する
- 方針:
  - CLI の実行方法は 1 パターンに固定する
  - GUI 操作ではなくコマンド起動を canonical にする
- 完了条件:
  - CLI の実行方法が 1 パターンに固定されている
  - 出力先と設定の扱いがドキュメント化されている
  - `Makefile` に将来反映すべきターゲットが整理されている

### Phase 4: 検証と文書整合

- 内容:
  - End-to-end 検証手順を確定する
  - `doc/03_実装カタログ.md` の更新対象を洗い出す
  - `doc/04_運用.md` の実行手順更新対象を洗い出す
  - サンプル入力確認、リンク整合確認を行う前提を置く
- 完了条件:
  - `01` `02` `03` `04` の記述が矛盾しない
  - 実行手順が上から辿れる
  - 実装後に何を検証すべきかが列挙済みである

## 3. End-to-end 検証

実装時に最低限満たすべき検証シナリオは以下とする。

### 3.1 正常系

- 小さな Markdown から PDF 生成
- テーブルを含む Markdown から PDF 生成
- コードブロックを含む Markdown から PDF 生成
- 引用を含む Markdown から PDF 生成

### 3.2 異常系

- 入力ファイル未存在
- フォント未導入
- 出力先ディレクトリ不正
- 依存未導入時の失敗

### 3.3 品質系

- 日本語文字化けなし
- A4 余白あり
- 見出しと本文の視認性確保
- 表とコードブロックが読める

### 3.4 文書整合

- `01` の仕様と `02` の Phase が対応している
- `02` の構成が `03` と `04` に引き継げる
- PDF を原本にしない運用が `04_運用.md` と矛盾しない

## 5. やらないこと（スコープ外）

- **Google Drive 連携** — 認証や同期運用が先に重くなるため
- **Web UI** — 初期版はローカル CLI を canonical にするため
- **複数 Markdown の一括バッチ変換** — v1 は単一入力 / 単一出力に絞るため
- **PDF 編集機能** — 本プロジェクトは生成パイプラインであり編集ツールではないため
- **OCR や注釈付与** — PDF 生成の本筋から外れるため
- **Pandoc 本命化** — 代替案には残すが初期実装の主軸にはしないため
- **Windows ネイティブ実装** — 初期対象環境を WSL に固定するため
- **GUI 操作依存の運用** — 再現性を落とすため
