# Markdown PDF Pipeline 仕様と設計

> 機能仕様 + アーキテクチャ設計。プロジェクト全体像を伝える土台。
> 要件レベルの変更時に更新する。矛盾時は [`02_移行ロードマップ.md`](./02_移行ロードマップ.md) を正とする。

## 共通前提

- **目的**: WSL 上で Markdown 原本から日本語 PDF を安定生成する。閲覧用の PDF を作ることが目的であり、原本は常に `.md` とする。
- **入力 / 出力**:
  - 入力 = UTF-8 の Markdown ファイル、任意の画像や相対リンク付きアセット、PDF レイアウト設定
  - 出力 = A4 前提の日本語 PDF、必要に応じて中間 HTML
- **担当範囲**: `WSL + Python` で完結する Markdown → PDF 変換パイプライン。Markdown 読み込み、HTML 化、CSS 適用、PDF 出力、ローカル保存までを扱う。
- **スコープ外**: Google Drive 連携、クラウド同期、自動共有、Web UI、複数人同時編集、PDF への注釈管理。
- **ユースケース**:
  1. ローカルの Markdown 文書を、読みやすい日本語 PDF に変換する。
  2. 表やコードブロックを含む技術文書を、レイアウト崩れを抑えて出力する。
  3. WSL 上で再現可能な形で PDF を作り、あとから手動で Windows 側や別サービスへ持ち出す。
- **開発環境**: WSL2 上の Ubuntu、Python 3、`pip` による依存導入、ローカル CLI 実行。
- **本番環境**: 同一 WSL 環境上での CLI 実行を本番とみなす。常駐サーバーは持たない。
- **言語 / フレームワーク**: Python。Markdown 解析ライブラリ + HTML/CSS ベース PDF 生成ライブラリを利用する。
- **設定管理**: 非機密は `env/config.yaml`、ローカル秘密情報は `env/secret.yaml`、共有・本番秘密情報は Doppler（`doppler.yaml`）。ただし本プロジェクトは原則として秘密情報を必要としない。
- **CI/CD**: 現時点では未整備。まずはローカル CLI の再現性を優先する。

## 1. アーキテクチャ

このプロジェクトは、Markdown 文書を Python で HTML に変換し、その HTML を CSS 付きで PDF にレンダリングするバッチ型パイプラインとして設計する。

```text
Markdown (.md)
   │
   ▼
[1] 入力読込・パス解決
   │
   ▼
[2] Markdown → HTML 変換
   │
   ▼
[3] HTML テンプレート適用
   │
   ▼
[4] 印刷用 CSS 適用
   │
   ▼
[5] PDF レンダリング
   │
   ▼
PDF (.pdf)
```

### コンセプト

- **Markdown を原本にする**: PDF は配布物であり、編集の起点にしない。
- **Python 主導で再現性を持たせる**: GUI 操作やエディタ拡張に依存せず、同じコマンドで同じ出力を狙う。
- **日本語 PDF を最初から前提にする**: フォント未指定による文字化けを避けるため、日本語フォント設定を設計に含める。
- **Google Drive は後回しにする**: まずはローカル完結で確実に PDF を作ることを優先する。

### 1.1 主要コンポーネント

| コンポーネント | 役割 |
|---|---|
| CLI エントリーポイント | 入出力パスと設定を受け取り、全処理を起動する |
| Markdown 変換層 | Markdown を HTML 断片へ変換する |
| HTML テンプレート層 | `html`, `head`, `body` を補い、文書全体の骨格を作る |
| CSS スタイル層 | フォント、余白、見出し、表、コードブロックの印刷スタイルを定義する |
| PDF レンダラ | HTML + CSS から PDF を生成する |
| 出力管理層 | 出力先パス作成、上書き制御、ログ出力を行う |

### 1.2 想定する処理フロー

1. Markdown ファイルパスを受け取る
2. UTF-8 で本文を読み込む
3. Markdown 拡張を有効化して HTML 化する
4. 文書タイトルやメタ情報を埋め込んだ HTML テンプレートに流し込む
5. A4 用 CSS と日本語フォント設定を適用する
6. PDF を所定の出力先へ書き出す

## 2. 機能仕様

### 2.1 Markdown 読み込み機能

- 単一の Markdown ファイルを入力とする
- 文字コードは UTF-8 を前提とする
- 相対パス基準で画像やリンクを解決できるよう、`base_url` を扱う
- 入力ファイルが存在しない場合は即時エラーにする

### 2.2 Markdown → HTML 変換機能

- Python ライブラリで Markdown を HTML に変換する
- 最低限、以下の記法に対応する
  - 見出し
  - 箇条書き
  - 強調
  - テーブル
  - フェンスコードブロック
  - 引用
- 想定する拡張は以下
  - `extra`
  - `tables`
  - `toc`
  - `fenced_code`

### 2.3 HTML テンプレート適用機能

- 変換後 HTML 断片を、そのまま PDF 化せず完全な HTML 文書へ包む
- `lang="ja"` と `meta charset="utf-8"` を含める
- タイトルは入力ファイル名を初期値とする
- 後段の CSS 適用を前提に、意味的な HTML 構造を壊さない

### 2.4 PDF スタイル適用機能

- A4 サイズを前提にする
- 余白は読みやすさ優先で確保する
- 日本語フォントとして `Noto Sans CJK JP` 系を優先する
- 最低限、以下の見た目を整える
  - 本文
  - `h1`〜`h3`
  - テーブル
  - `code` / `pre`
  - `blockquote`
- 横長テーブルは完全解決せず、Markdown 側での構造見直しも前提とする

### 2.5 PDF 出力機能

- HTML + CSS から PDF を生成する
- 出力ファイル名は入力ファイル名ベースで決定する
- 既定の出力先は入力と同じディレクトリ、または明示指定ディレクトリとする
- 正常終了時は生成ファイルパスを標準出力へ出す

### 2.6 エラー処理

- 入力ファイル未存在
- フォント未導入
- PDF レンダリング失敗
- 依存ライブラリ未導入

これらは黙って握りつぶさず、CLI で失敗理由を表示して終了する。

## 3. 設計上の決定事項

### 3.1 採用したアプローチ

- **Python + WeasyPrint 系を採用する**: WSL 上で Python 主導に寄せやすく、HTML/CSS ベースで見た目調整もしやすい。
- **HTML を中間表現にする**: Markdown を直接 PDF に落とすより、途中で HTML を経由した方が構造とスタイルを分離しやすい。
- **日本語フォントを明示指定する**: `Noto Sans CJK JP` 系を前提にし、文字化けや豆腐化を避ける。
- **ローカル完結を優先する**: まずは `Markdown -> PDF` の核を安定させ、外部サービス連携は後段に回す。

### 3.2 採用しなかったアプローチ

- **Google Drive 連携を初期スコープに入れる**: 共有や同期を先にやると、変換コアの安定化より認証や運用が先に重くなるため不採用。
- **VS Code 拡張依存を主軸にする**: 手軽だが、再現性と自動化の観点で弱い。
- **PDF を原本にする運用**: 修正・差分管理・再生成性が落ちるため不採用。
- **Pandoc + XeLaTeX を初期実装の本命にする**: 出力品質は高いが、今回の主題は `WSL + Python` で完結する最初の実装なので主軸にはしない。

### 3.3 技術選定の判断

| 候補 | 判断 |
|---|---|
| Python + WeasyPrint | 採用。本命 |
| Pandoc + XeLaTeX | 代替案。高品質だが初期本命ではない |
| VS Code 拡張 | 手動利用の補助候補 |
| Google Drive 連携 | 後回し |

## 4. 非機能要件

- **性能 / スケール**: 単一 Markdown 文書をローカルで数秒から数十秒で PDF 化できることを目安とする。大量バッチは初期対象外。
- **セキュリティ / 認証**: 初期版はローカル完結で認証不要。秘密情報を使わない設計を維持する。
- **可用性 / 監視**: 常駐サービスではないため監視は不要。CLI 実行が成功することを品質基準にする。
- **再現性**: 同じ入力、同じフォント、同じ依存バージョンで同一系統の PDF が生成されること。
- **日本語品質**: 文字化けせず、日本語見出し・本文・表・コードが読めること。
- **保守性**: CSS 調整と変換ロジックを分離し、レイアウト変更がコード本体を壊しにくい構成にする。
- **運用性**: 1 コマンドで PDF を作れる形を目指す。

## 5. 破綻条件

以下の状態は設計破綻とみなす。

| 破綻条件 | 内容 | 対策 |
|---|---|---|
| フォント未指定 | 日本語が文字化けする | 日本語フォントを明示指定する |
| PDF を原本化 | 修正フローが壊れる | Markdown を唯一の原本にする |
| 横長表に依存 | PDF で可読性が崩れる | Markdown 側でカード化や分割を検討する |
| 外部連携を先に広げる | 変換コアが固まる前に複雑化する | Google Drive は後回しにする |
| GUI 手順依存 | 再現性が落ちる | CLI ベースで固定する |
